# Generic Parsing Algorithm(通用資料爬取)

設計定稿(2026-08-11 grill 後收斂)。互動基礎沿用紅框工具,參見 @../red-outline/index.html

## 目標與產出

Bookmarklet。使用者以紅框框選兩個「資料意義上同層級」的元素,工具自動:

- **綠框**:兩紅框的最近共同祖先(可調整)
- **查詢判斷式**:以綠框為參考點的相對 XPath
- **藍框**:判斷式命中的所有元素

最終產出(工具列按鈕):

1. **複製查詢式**:綠框絕對 XPath + 判斷式,供外部爬蟲程式使用
2. **抽取文字**:藍框元素 textContent,一行一筆複製到剪貼簿

註:早期設計分「基本型(紅框選三)/進階型(紅框選二)」兩種模式,已收斂為單一模式 —
紅框選三的效果(多層轉星)由 pill 點選取代,舊基本型即「還沒動 pill 時的自動預設狀態」。

## 操作流程

1. 啟用後,hover 顯示**橘色虛線**預覽框(藍色保留給查詢結果,避免混淆)
2. 左鍵標紅框,上限 2;**右鍵**取消
   - 與現有紅框呈祖先/後代關係(巢狀)→ 標記當下拒絕,提示「請框選平行元素」
   - 左鍵點在已標記的紅框(或其後代)上 = 開啟該紅框的**祖先選單**(見「紅框調層」)
3. 紅框滿 2 → 自動綠框 + 判斷式 + 藍框,並顯示 pills 橫框
4. pills 橫框內容:`[⬆][⬇]` 綠框逐層移動 + 判斷式節點 pills + 藍框計數 +
   `複製查詢式` `抽取文字` `清除` `結束`
5. 紅框滿 2 後:
   - 點擊兩紅框的共同祖先 = 綠框直接跳到該層(雙向,可調遠也可調近)
   - `⬆⬇` 按鈕與點擊等效 — 解決祖先被子元素 100% 鋪滿、`elementFromPoint` 永遠點不到的問題(list/grid 版面常態)
   - 點擊紅框或其後代 → 開該紅框的祖先選單;點擊其他元素 → 忽略 + 提示

## 演算法

### 表記即執行

Pill 顯示什麼,查詢就執行什麼,不做任何轉換。
`tag[*]` 的真實 XPath 語意是「有至少一個元素子節點」:

- 出現在**中間節點**時是無害的恆真過濾(路徑後續本來就要求有元素子節點),結果不變
- 出現在**最末節點**時會濾掉純文字元素 — 這是刻意開放的第三態(見 pill 規則)

### 主流程

輸入:紅框 A、B 相對最近共同祖先(NCA)的路徑 p1、p2,每節記為 `tag[序號]`。

1. **對稱**:|p1| = |p2| 且標籤序列相同
   → `./` + 逐層比對:序號相等 → 保留 `[n]`;相異 → 轉星
2. **否則**從尾端逐節往前比對(標籤+序號完全相等),得最大共同後綴 S:
   - |S| = 0 → 無效框選(無共同結尾)
   - 恰有一側剩餘為空 → **不對稱**(裝飾父層:有些設計會包額外父層做裝飾,
     但紅框兩元素資料意義上同層級)→ `.` + `//` + S;
     S 首節因兩側父層不同、序號失去比較意義,**強制轉星**
   - 兩側皆有剩餘(= 出現兩種以上裝飾父層,預期最多一種)→ 先拒絕,有實際案例再擴充

`//` 只插在分歧點;對稱案例維持 `./`,不會出現 `//`。

3. **轉星的呈現**:中間節點 → `[*]`;最末節點 → 預設「無 predicate」(選取全部)。
   最末節點若預設 `[*]` 會照字面濾掉純文字元素,連紅框自己都可能不在藍框內,故預設裸標籤。

### 綠框調遠

舊綠框到新綠框之間的層級,以前綴加入判斷式並**自動轉星**;
但該層元素在其父層下沒有同標籤 sibling 時,維持 `[1]` 且 pill disabled。

## Pill 規則

- **可點性**:該層元素在其父層下同標籤數 > 1 才可點(僅以紅框/綠框鏈所在的具體父層計數 — 保守版,之後有實際需求再擴充)
- **中間節點**:兩態循環 `[n]` ↔ `[*]`
- **最末節點**:三態循環 `[n]` → 無 predicate → `[*]` → `[n]`
- **強制轉星節點**(序號相異或 `//` 首節,無單一序號可還原):
  - 中間節點:鎖定 `[*]`
  - 最末節點:兩態循環 無 predicate ↔ `[*]`
- **綠框鏈節點**(調遠新增):預設 `[*]`;無 sibling 時鎖定 `[1]`

## 紅框調層

紅框常常只點得到裡面的 `<a>`,點不到外面的 `<li>` —— 與綠框 `⬆⬇` 同一個理由的鏡像:
祖先被子元素 100% 鋪滿時 `elementFromPoint` 永遠取不到它。

左鍵點紅框(或其任何後代,判定同右鍵取消的 `r === cur || r.contains(cur)`)開啟選單:

```
tag[n] › tag[n] › tag[n]  │  ⇄ 另一框也上移 N 層  │  ✕
                  ██████
              目前層反白不可點
```

### 錨點模型

每個紅框記住 **origin** —— 使用者最初點的那個元素(`Map<目前紅框元素 → origin>`)。
紅框只能沿 `parentElement` 鏈移動,所以它任何時刻的位置**必定**在 `segsUp(origin)` 上;
「走過的路徑」是可推導的,不另存堆疊。

- **pills** = origin 到天花板的完整可走鏈,由高到低,目前層反白
- **天花板** = 不得包住另一個紅框(否則違反紅框不可巢狀);只有一個紅框時 = `body` 的直接子元素
- **復歸原點** = 點最右邊那顆 pill
- **分隔符用 `›`** 而非 `/` —— 與工具列的判斷式 pills 區隔:那些切 predicate,這些跳層

hover 任一 pill(或同步鈕)→ 橘色虛線框畫到目標層 + tip 顯示標籤。
需要 `previewEl` 旗標讓 `move()` 早退,否則游標在 pill 上微動就會被 `hide()` 擦掉。

### 移動語意

**只搬選中的那一個。** 對稱案例中途必然掉進「兩紅框無共同結尾」,工具列紅字提示,
搬另一個即復原 —— 這是可接受的暫態,不是要防的錯誤。不做強制連動:
不對稱模式下兩紅框深度本來就不同,「一起升一層」沒有一致的定義,
而且兩者的天花板不同,一個先到頂就得整個 disable。

### 同步鈕(⇄)

以 origin 為基準的**上升層數**對齊,是當下狀態的推導值而非暫存旗標:

```
offset(紅) = segsUp(origin).length − segsUp(紅).length
顯示條件:兩 offset 不等 ∧ 補齊位置在鏈上且不撞天花板 ∧ 試算 model 非 err
動作:把落後者補到相同 offset
```

兩個紅框的選單都有這顆,做的是同一件事,關掉選單再開它還在。
選 offset 對齊而非「絕對深度對齊」:origin 已經是使用者對齊過的基準,
裝飾父層案例的深度差正是 `//` 存在的理由,抹平了反而把正確的框選搞壞。

按鈕文字寫「另一框」而不寫「紅2」—— 畫面上兩個紅框長得一模一樣,序號對使用者無意義;
hover 時橘框直接畫在另一個紅框將要去的那一層上,不需要命名。

### 選單生命週期

黏著式:點 pill 只搬層不關,選單重新錨到新紅框左上外側 6px(越界翻到下緣 / clamp)。

| 事件 | 行為 |
|---|---|
| 點頁面其他地方 | 只關選單,**吃掉那一下**(誤標紅框會清 overrides、重建深入模式的樹,代價太高) |
| `Esc` | 選單開 → 只關選單;選單關 → 結束工具(同 modal 的階層) |
| 捲動 | 關閉 |
| 目標紅框消失(`✕`、右鍵、清除、結束) | 關閉 |
| 深入 modal 開啟中 | 不開選單 |

### 失效規則

**紅框往上搬不會改變 NCA。** `findNCA(a, b)` 是從 `a.parentElement` 往上走到第一個 `contains(b)`,
把 `a` 換成它的某個祖先(依天花板定義該祖先仍不含 `b`),起點雖然變高,終點完全一樣。

所以綠框沒有理由重置,連帶 `chain = segsUp(nca, green)` 也逐字相同:

| 狀態 | 搬層後 |
|---|---|
| `green` | **保留**(`build(true)`) |
| chain 覆寫(元素鍵) | **保留** |
| tail 覆寫(`'T…'` 字串鍵) | **清除** |
| 深入模式的樹與勾選 | `reds[0]` 搬層即樣本列換人 → 重建 + 提示(現有 `tplEl !== reds[0]` 自動涵蓋) |

tail 鍵是 `'T' + (nodes.length - 1 - ix)`,**從尾端倒數**。上升一層 tail 少一節,
舊 `T1` 遞補成新 `T0`,設定整個錯位一格。不做位移重映射:`overrides` 存的是**索引**不是狀態名,
中間節點二態 `[n]/[*]`、最末節點三態 `[n]/裸/[*]`,同一個 `si=1` 兩邊分別是 `[*]` 與裸標籤,
映射過去會安靜地變意思,而 `si >= states.length` 那道防線擋不到。

### 實作陷阱:搬層目標可能正是藍框

`//` 模式下判斷式如 `.//div` 會命中巢狀的同名祖先。單框上移**不必然**造成 err ——
`asym` 分支只要求從尾端逐節 tag+idx 全等、且恰有一側先耗盡:

```
green ├ div[1] ─ div[1] ← 紅1      初始對稱 ./div[*]/div[1],blues = 18
      ├ div[2] ─ div[1] ← 紅2
      ⋮ (共 20 列)

紅1 上移 → p1'=[div[1]], p2=[div[2],div[1]]
           尾端 div[1] vs div[1] 全等 → S=[div[1]], 一側耗盡 → asym 成立
        → .//div   matched 從 20 變 40(內外層通吃),blues = 38
        → 外層 div[2](紅2 的父層)現在是藍框
```

此時把紅2 上移,目標正是一個藍框。naive 寫法會讓紅2 消失:

```
outline(div[2], 紅)          prev 已被藍框佔用,不覆寫(保留原始樣式)
build() → blues.forEach(restore)      div[2] 還原成原始樣式,紅色被抹掉
       → matched.forEach(… reds.indexOf(el) < 0 …)   跳過紅框,不補畫
```

既有邏輯沒有錯 —— 既有流程裡不存在「在已有藍框的狀態下把紅框換成它的祖先」這個動作
(`mark()` 加第二個紅框時 `reds.length < 2`,`build()` 早退,藍框陣列必定是空的)。
危險由本功能引進,修正也侷限在搬層 handler:

```js
restore(舊); blues.forEach(restore); blues = [];   // ← 先清藍框再上色
outline(新, '3px solid #c8102e', '-2px'); reds[i] = 新; build();
```

另外同步鈕的試算需要在不動 DOM 的前提下判斷「套用得成功嗎」,
故將 `build()` 的純計算部分抽成 `computeModel(r0, r1, nca, green)`(唯讀,只讀 `overrides`)。

## 案例

所有案例皆以 `/root[1]/sect[1]` 為最近共同祖先出發,判斷式相對綠框。

### 對稱父層

紅框 `div[3]` 和 `div[4]`
→ `./div`(最末節點強制轉星 → 裸標籤;藍框 = sect 下所有 div)
div pill 可切換 無 ↔ `[*]`

### 對稱祖先

紅框 `div[3]/span[2]` 和 `div[4]/span[2]`
→ `./div[*]/span[2]`
span pill 三態:`[2]` → `span` → `[*]` → `[2]`

### 不對稱(裝飾父層)

紅框 `aside[1]/div[1]` 和 `div[1]`
→ 共同後綴 `div[1]`,剩餘 `aside[1]` vs 空 → `.//div`

### 不對稱深層

紅框 `aside[1]/div[1]/span[2]` 和 `div[1]/span[2]`
→ 共同後綴 `div[1]/span[2]` → `.//div[*]/span[2]`
(div 為 `//` 首節強制轉星;span 序號相等保留)

### 綠框調遠

上例綠框 ⬆ 至 `/root[1]`:
- root 下有多個 sect → `./sect[*]//div[*]/span[2]`
- root 下僅一個 sect → `./sect[1]//div[*]/span[2]`(sect pill disabled)

### 對稱 + 綠框調遠

紅框 `sect[1]/div[1]` 和 `sect[1]/div[2]`(綠框 `/root[1]`)
→ `./sect[*]/div`(對稱無 `//`;sect 自動轉星、div 終端裸標籤)

## 拒絕條件一覽

| 情況 | 時機 | 行為 |
|---|---|---|
| 巢狀紅框 | 標記當下 | 拒絕 + 提示 |
| 無共同結尾(\|S\| = 0) | 紅框滿 2 | 判斷式 null + 提示重選 |
| 兩種以上裝飾父層 | 紅框滿 2 | 拒絕(暫不支援) |
| 滿 2 後點非共同祖先、且不在紅框內 | 點擊當下 | 忽略 + 提示 |
| 紅框調層會包住另一個紅框 | 選單渲染當下 | 該層不長出 pill(天花板) |

## 實作備註

- 事件於 capture 階段攔截(沿用紅框工具),`elementFromPoint` 取得目標;無需 `composedPath`
- 查詢一律以當前綠框為參考點:`document.evaluate(判斷式, 綠框節點, null, ORDERED_NODE_SNAPSHOT_TYPE, null)`
- 抽取文字:藍框(含紅框)元素依 DOM 順序,`textContent` 摺疊空白後一行一筆
- 已知限制:嚴格 CSP 站點、iframe 內容、SVG/命名空間元素
